# Design

## 1. Настройки скрыты по умолчанию

Восемь чисел создаются с `entity_registry_enabled_default=False`. В блоке настроек устройства их
нет, пока пользователь не включит нужную сущность: **Настройки сущности → Включить**.

Почему так, а не отдельной опцией: опция включала бы все восемь сразу, а человеку обычно нужны одна
или две. Штатное включение сущности решает задачу точнее, ничего не ломает и не требует новых
ключей переводов. Домены не меняются — `number` остаётся `number`, история сущности сохраняется.

Почему не показать значения отдельными датчиками: это меняло бы домен при включении и обратно,
обнуляя историю. Владелец 0.2.0, у которого числа уже включены, такое заметил бы сразу.

Важно: `entity_registry_enabled_default` действует только в момент регистрации сущности. У тех, кто
уже поставил 0.2.0 и включил числа, они останутся включёнными — это и правильно, и безопасно:
человек их уже видел и правил.

## 2. Параметры шины: только диалог

В блоке настроек их нет вообще. Правка — в диалоге параметров устройства (**Настроить** у записи):

```
init → три поля: адрес (1…247), скорость, чётность; предупреждение в описании
     → bus_settings_confirm: подтверждение «связь пропадёт»
     → запись
```

**Форма.** Поля заполнены текущими значениями датчика. Предупреждение прямо в описании:

> Запись этих параметров обрывает связь: датчик начнёт отвечать по новым адресу, скорости и
> чётности, а запись продолжит ходить по старым. Сущности станут недоступны, пока вы не
> переконфигурируете запись.

**Подтверждение.** Второй шаг с флажком «Понимаю, что связь пропадёт». Без согласия ничего не
пишется, диалог закрывается.

**Если ничего не меняли.** Значения совпадают с текущими — диалог просто закрывается, записи и
ремонта нет. Иначе каждая отмена превращалась бы в «связь потеряна».

**Одно обращение.** Три значения уходят одной операцией `0x10` по регистрам `0x0007…0x0009` через
`settings.async_write_link_settings` из библиотеки 0.5.0. Параметры подключения самой записи
интеграция не меняет: при неверном значении это оставило бы запись без устройства и без пути назад.

**После записи.** Ремонт `bus_settings_changed` с новыми значениями и инструкцией, предупреждение в
журнале, перезагрузка записи. Опрос, естественно, не проходит: датчик отвечает по новым параметрам.

## 3. Код MAC

Датчик «Код MAC»:

- значение — `settings.mac_code`, целое без преобразования;
- категория `DIAGNOSTIC`, `entity_registry_enabled_default=False`;
- имя и описание в переводах говорят, что это один регистр, а не полный MAC-адрес.

`mac_code` добавляется в список полей, которые выгружает диагностика.

## 4. Что остаётся как было

- проверка кода состояния перед записью обычного параметра;
- проверка правила суммы зон с понятным сообщением;
- ошибки записи: неготовность, отказ, расхождение, нет связи;
- перечитывание настроек раз в минуту;
- версия 0.3.0.

## 5. Про `type: simple-entity`

В документации дашбордов есть опция строки карточки `entities`, которая рисует сущность простым
состоянием без элемента управления. Для страницы устройства она не годится: блок настроек рисует
фронтенд сам, а запись при этом не запрещается — число остаётся числом. Пользователю она полезна
иначе: включённую настройку можно показать на дашборде только для чтения. Совет уходит в README.

## 6. Проверка на живом устройстве

- запись трёх регистров одним запросом принимается, значения читаются обратно с новыми параметрами;
- при неизменённых значениях диалог ничего не пишет;
- после записи появляется ремонт, опрос не проходит, переконфигурация возвращает устройство;
- код MAC виден в сенсоре и в диагностике.

## 7. Риски

| Риск | Снижение |
|---|---|
| пользователь меняет параметры шины, не понимая последствий | предупреждение на форме и подтверждение; ремонт с инструкцией |
| запись трёх регистров отклонена | ошибка показывается до перезагрузки записи, значения не применены |
| настройки не видны и выглядят пропавшими | в README сказано, как включить нужную сущность |
