# Spec Delta

## Purpose

Когда датчик ведёт себя странно — не видит человека, постоянно показывает присутствие или не
отвечает — пользователю и сопровождающему нужно понять причину. Для этого интеграция показывает
состояние самого устройства, версии прошивок и выгружает диагностику.

## ADDED Requirements

### Requirement: Диагностическая сущность состояния устройства

Для каждого датчика интеграция SHALL создавать сущность состояния устройства с категорией
«диагностика», выключенную по умолчанию. Значение берётся из свойства `status` библиотеки
`mtdx62` и показывается текстом из переводов.

#### Scenario: Идёт самопроверка

- **WHEN** библиотека сообщает код состояния 0
- **THEN** диагностическая сущность состояния показывает «идёт самопроверка»

#### Scenario: Устройство работает

- **WHEN** библиотека сообщает код состояния 1
- **THEN** диагностическая сущность состояния показывает «работает»

#### Scenario: Самопроверка не пройдена

- **WHEN** библиотека сообщает код состояния 2
- **THEN** диагностическая сущность состояния показывает «самопроверка не пройдена»

#### Scenario: Неисправность радара

- **WHEN** библиотека сообщает код состояния 4
- **THEN** диагностическая сущность состояния показывает «неисправность радарного модуля»

#### Scenario: Неисправность связи RS485

- **WHEN** библиотека сообщает код состояния 5
- **THEN** диагностическая сущность состояния показывает «неисправность RS485»

### Requirement: Неизвестный код состояния показывается, а не скрывается

Если библиотека сообщает `status = None` при заданном `status_code`, сущность состояния MUST
показывать «неизвестный код» и MUST NOT становиться `unavailable`. Исходный код MUST попадать в
диагностику.

#### Scenario: Неизвестный код состояния

- **WHEN** библиотека сообщает код состояния 9
- **THEN** диагностическая сущность состояния показывает «неизвестный код» и остаётся доступной

### Requirement: Диагностические сущности версий прошивки

Интеграция SHALL создавать диагностические сущности версии приложения и версии радарного модуля,
выключенные по умолчанию. Значения берутся из свойств `app_version` и `radar_version` библиотеки.

#### Scenario: Версии прошивки

- **WHEN** библиотека сообщает `app_version = 1.2.3` и `radar_version = 0.1.2`
- **THEN** сущность версии приложения показывает `1.2.3`, а сущность версии радара — `0.1.2`

### Requirement: Сведения об устройстве в реестре

Интеграция SHALL заполнять в реестре устройств производителя («Zhejiang Oujue Electronic
Technology»), модель, выбранную пользователем при добавлении, и версию приложения, когда она
прочитана.

#### Scenario: Карточка устройства

- **WHEN** пользователь открывает страницу устройства
- **THEN** в ней указаны производитель, модель и версия приложения

### Requirement: Выгрузка диагностики

Интеграция SHALL поддерживать скачивание диагностики для записи конфигурации и для устройства
в соответствии с `conventions/diagnostics`.

В диагностике MUST быть: параметры связи, текущие значения измерений, прочитанные параметры
устройства, версии и сырые регистры. Путь к последовательному порту и код MAC MUST быть вырезаны.

#### Scenario: Скачивание диагностики устройства

- **WHEN** пользователь скачивает диагностику устройства
- **THEN** файл содержит модель, адрес на шине, текущие измерения, параметры устройства, версии и
  сырые регистры, а путь к последовательному порту заменён указанием, что он скрыт

#### Scenario: Параметры читаются при выгрузке

- **WHEN** пользователь скачивает диагностику, а параметры устройства ещё ни разу не читались
- **THEN** интеграция читает их в этот момент и включает в файл

#### Scenario: Датчик не отвечает при выгрузке

- **WHEN** пользователь скачивает диагностику, а датчик не отвечает
- **THEN** файл всё равно формируется: в нём есть параметры связи и пометка, что данные с
  устройства получить не удалось

#### Scenario: Датчик неисправен, но отвечает

- **WHEN** датчик сообщает код состояния 4 и пользователь скачивает диагностику
- **THEN** в файле есть прочитанные значения измерений и сырые регистры, даже если сущности
  измерений в интерфейсе недоступны

### Requirement: Ремонт при зависании в самопроверке

Код состояния 0 — нормальное состояние первые секунды после включения. Если он держится дольше
60 секунд подряд, интеграция SHALL создавать repair issue, потому что дальше это уже не загрузка,
а зависание, и устранить его может только пользователь, выключив питание.

Repair MUST создаваться один раз и MUST удаляться, как только код состояния сменился на любой
другой, а также при выгрузке записи.

#### Scenario: Самопроверка зависла

- **WHEN** датчик сообщает код 0 в течение нескольких минут
- **THEN** в Home Assistant появляется repair issue с названием устройства, и оно остаётся одно,
  сколько бы опросов ни прошло

#### Scenario: Самопроверка завершилась штатно

- **WHEN** датчик сообщает код 0 несколько секунд, а затем код 1
- **THEN** repair issue не создаётся

#### Scenario: Датчик вышел из самопроверки с ошибкой

- **WHEN** после созданного repair issue код состояния меняется на 4
- **THEN** repair issue удаляется, а неисправность видна в сущности состояния

### Requirement: Сообщение о неисправности в журнале

Если библиотека сообщает код неисправности, то есть код от 2 и выше, интеграция MUST записывать
это в лог один раз при появлении неисправности и один раз при её исчезновении, а не на каждом
опросе. Коды 0 (идёт самопроверка) и 1 (устройство работает) неисправностью не считаются.

#### Scenario: Появилась и исчезла неисправность

- **WHEN** датчик пять опросов подряд сообщает код 4, а затем код 1
- **THEN** в логе появляется одна запись о неисправности и одна запись о её устранении

#### Scenario: Самопроверка после включения

- **WHEN** датчик сразу после включения сообщает код 0, а через пару секунд код 1
- **THEN** записей о неисправности в логе не появляется
